### 1.3 [`config.py`](../nanovllm/config.py) —— 所有可调旋钮

```python
@dataclass(slots=True)
class Config:
    model: str
    max_num_batched_tokens: int = 16384   # 一步 prefill 最多算多少 token
    max_num_seqs: int = 512               # 一个 batch 最多多少序列
    max_model_len: int = 4096             # 模型支持的最大序列长度
    gpu_memory_utilization: float = 0.9   # 显存利用率上限
    tensor_parallel_size: int = 1         # 张量并行卡数
    enforce_eager: bool = False           # 是否禁用 CUDA graph（调试用）
    hf_config: AutoConfig | None = None   # HuggingFace 模型配置（post_init 里填）
    eos: int = -1                         # 结束符 token id（llm_engine 里填）
    kvcache_block_size: int = 256         # KV cache 块大小（必须是 256 的倍数）
    num_kvcache_blocks: int = -1          # 块数（allocate_kv_cache 里算）

    def __post_init__(self):
        assert os.path.isdir(self.model)
        assert self.kvcache_block_size % 256 == 0
        assert 1 <= self.tensor_parallel_size <= 8
        self.hf_config = AutoConfig.from_pretrained(self.model)
        self.max_model_len = min(self.max_model_len, self.hf_config.max_position_embeddings)
```

- 这里用到的 `@dataclass(slots=True)` / `__post_init__` / `X | None`，原理见 [第 3 部分 A1/A2/A4](03-Python语法清单.md)。
- `__post_init__` 做的事：校验 + 加载 hf_config + 把 `max_model_len` 裁剪到不超过模型支持的上限（`max_position_embeddings`，这是 RoPE 能编码的最大位置）。
- 末尾两个字段 `eos` 和 `num_kvcache_blocks` 初始是 -1，**运行时才填**——它们依赖 tokenizer（eos）和显存测量（块数）。

> 💡 回顾 [第 2b 部分](02b-引擎核心机制.md)：`kvcache_block_size=256`、`num_kvcache_blocks` 这两个字段，正是 PagedAttention 的核心参数。

### 1.4 [`sampling_params.py`](../nanovllm/sampling_params.py) —— 采样参数

```python
@dataclass(slots=True)
class SamplingParams:
    temperature: float = 1.0
    max_tokens: int = 64
    ignore_eos: bool = False

    def __post_init__(self):
        assert self.temperature > 1e-10, "greedy sampling is not permitted"
```

- [第 2c 部分 §5](02c-加速并行与采样.md) 讲过：`temperature` 是采样的"随机度旋钮"。这里**禁止 temperature=0**（贪心解码），因为 nano-vllm 的采样器用的是 Gumbel-max 变体，要求 temperature>0。

## 层 2：引擎层（核心）

### 2.1 [`engine/sequence.py`](../nanovllm/engine/sequence.py) —— 一个请求的"档案袋"

回顾 [第 1 部分](01-全局视角.md)：Sequence 是一个推理请求从生到死的档案。现在看它的代码。

#### 状态机

```python
class SequenceStatus(Enum):       # 第3部分 A6: Enum + auto()
    WAITING = auto()              # 刚进来，等着 prefill
    RUNNING = auto()              # prefill 完，正在 decode
    FINISHED = auto()             # 生成完（到 EOS 或 max_tokens）
```

#### 字段：档案袋里装了什么

```python
class Sequence:
    block_size = 256              # 类属性（所有实例共享），由 LLMEngine 设置
    counter = count()             # 类属性：全局 ID 生成器（第3部分 C3）

    def __init__(self, token_ids, sampling_params=SamplingParams()):
        self.seq_id = next(Sequence.counter)        # 唯一递增 id
        self.status = SequenceStatus.WAITING
        self.token_ids = copy(token_ids)            # 第3部分 C5: copy 防误改
        self.last_token = token_ids[-1]             # 最后一个 token（decode 用）
        self.num_tokens = len(self.token_ids)       # 当前总长度
        self.num_prompt_tokens = len(token_ids)     # prompt 长度（不变）
        self.num_cached_tokens = 0                  # 已经算过并存进 KV cache 的长度
        self.num_scheduled_tokens = 0               # 本步要算的长度
        self.is_prefill = True
        self.block_table = []                       # ★ PagedAttention 页表（第2b部分）
        self.temperature = sampling_params.temperature
        self.max_tokens = sampling_params.max_tokens
        self.ignore_eos = sampling_params.ignore_eos
```

> 🔑 重点理解两组"长度"字段（最容易混）：
> - `num_tokens`：序列**当前**的总长度（随生成增长）。
> - `num_prompt_tokens`：原始 prompt 长度（固定）。`num_tokens - num_prompt_tokens` = 已生成的 completion 长度。
> - `num_cached_tokens`：**已经算过并写进 KV cache** 的长度。chunked prefill 时它可能 < num_tokens（分批算）。
> - `num_scheduled_tokens`：**本步**要算的长度（prefill 时可能是一大段，decode 时是 1）。

#### 派生属性（property）

```python
@property
def num_blocks(self):
    return (self.num_tokens + self.block_size - 1) // self.block_size   # 向上取整除法

@property
def last_block_num_tokens(self):
    return self.num_tokens - (self.num_blocks - 1) * self.block_size    # 最后一个块装了几个 token
```

- `num_blocks`：序列**需要**几个块。`(a + b - 1) // b` 是经典的"整数向上取整除法"技巧（等价于 `ceil(a/b)` 但不用浮点）。
- `last_block_num_tokens`：最后一个块目前装了几个 token（1 ~ block_size）。decode 写 KV cache 时要用它定位 slot。

#### `block(i)`：取第 i 个逻辑块的 token

```python
def block(self, i):
    assert 0 <= i < self.num_blocks
    return self.token_ids[i*self.block_size : (i+1)*self.block_size]   # 切片
```

这给 block_manager 算哈希用（[第 2b 部分 §4](02b-引擎核心机制.md) 的 prefix caching）。

#### 自定义序列化（重点）⭐

```python
def __getstate__(self):
    last_state = self.last_token if not self.is_prefill else self.token_ids
    return (self.num_tokens, self.num_prompt_tokens, self.num_cached_tokens,
            self.num_scheduled_tokens, self.block_table, last_state)
```

[第 3 部分 B2](03-Python语法清单.md) 讲过：这是为了**多进程传输时省数据**。decode 阶段只传 `last_token`（1 个 int），不传完整 token_ids（可能几千个 int）。详见前面的解释。

#### 数据模型协议

```python
def __len__(self):          # 第3部分 B1: 支持 len(seq)
    return self.num_tokens
def __getitem__(self, key): # 支持 seq[i], seq[a:b]
    return self.token_ids[key]
def append_token(self, token_id):   # 生成新 token 时调用
    self.token_ids.append(token_id)
    self.last_token = token_id
    self.num_tokens += 1
```

### 2.2 [`engine/block_manager.py`](../nanovllm/engine/block_manager.py) —— KV cache 分页管家

这是 PagedAttention + Prefix Caching 的实现（理论见 [第 2b 部分](02b-引擎核心机制.md)）。我们重点看几个最精妙的函数。

#### Block 数据结构

```python
class Block:
    def __init__(self, block_id):
        self.block_id = block_id
        self.ref_count = 0        # 引用计数（前缀共享用）
        self.hash = -1            # 内容指纹（prefix cache 用，-1=未算）
        self.token_ids = []       # 块内 token（算/校验 hash 用）
    def update(self, hash, token_ids):
        self.hash, self.token_ids = hash, token_ids
    def reset(self):
        self.ref_count = 1; self.hash = -1; self.token_ids = []
```

#### 链式哈希 compute_hash ⭐

```python
@classmethod
def compute_hash(cls, token_ids, prefix=-1):
    h = xxhash.xxh64()
    if prefix != -1:
        h.update(prefix.to_bytes(8, "little"))   # 前一块的 hash 当"盐"
    h.update(np.array(token_ids).tobytes())       # 本块 token
    return h.intdigest()
```

对应 [第 2b 部分 §4.3](02b-引擎核心机制.md)：`h_i = hash(h_{i-1}, tokens_i)`。`prefix=-1` 是起点（第一个块没有前驱）。

#### can_allocate：试探能否放下 + 命中几个前缀块

```python
def can_allocate(self, seq):
    h = -1
    num_cached_blocks = 0
    num_new_blocks = seq.num_blocks
    for i in range(seq.num_blocks - 1):         # 注意 -1：最后一个块可能没满，不参与匹配
        token_ids = seq.block(i)
        h = self.compute_hash(token_ids, h)     # 链式算哈希
        block_id = self.hash_to_block_id.get(h, -1)
        if block_id == -1 or self.blocks[block_id].token_ids != token_ids:  # 哈希命中还要校验内容！
            break
        num_cached_blocks += 1
        if block_id in self.used_block_ids:     # 命中的块若已在用，不占新块
            num_new_blocks -= 1
    if len(self.free_block_ids) < num_new_blocks:
        return -1                                # ★ 显存不够信号
    return num_cached_blocks
```

> 🔬 两个细节：
> 1. `range(seq.num_blocks - 1)`：**最后一个块不参与匹配**。因为最后一个块往往没填满（token 还在变），哈希不稳定。
> 2. `self.blocks[block_id].token_ids != token_ids`：哈希命中后还要**逐 token 校验内容**！因为哈希理论上可能碰撞（虽然 xxhash 碰撞概率极低）。这是"宁可慢一点也要正确"的工程严谨。

#### hash_blocks：postprocess 时登记新块的指纹

```python
def hash_blocks(self, seq):
    start = seq.num_cached_tokens // self.block_size
    end = (seq.num_cached_tokens + seq.num_scheduled_tokens) // self.block_size
    if start == end: return                     # 没跨过块边界，没有"新填满的块"
    h = self.blocks[seq.block_table[start-1]].hash if start > 0 else -1
    for i in range(start, end):
        block = self.blocks[seq.block_table[i]]
        token_ids = seq.block(i)
        h = self.compute_hash(token_ids, h)     # 链式
        block.update(h, token_ids)
        self.hash_to_block_id[h] = block.block_id
```

> 只对**新填满**的块（`start` 到 `end` 跨过的整块）算哈希。半满的块（`start==end`）跳过——它内容还会变，不能登记。

#### can_append 的取模技巧

```python
def can_append(self, seq):
    return len(self.free_block_ids) >= (len(seq) % self.block_size == 1)
def may_append(self, seq):
    if len(seq) % self.block_size == 1:
        seq.block_table.append(self._allocate_block())
```

[第 2b 部分 §3.4](02b-引擎核心机制.md) 讲过：`len(seq) % block_size == 1` 这个布尔值（True=1 / False=0）正好表示"是否需要新块"。`>= 1` 或 `>= 0` 一目了然。极其简洁。

### 2.3 [`engine/scheduler.py`](../nanovllm/engine/scheduler.py) —— 调度大脑

理论见 [第 2b 部分 §5](02b-引擎核心机制.md)。这里带代码过一遍 `schedule()`。

#### 数据结构

```python
class Scheduler:
    def __init__(self, config):
        self.max_num_seqs = config.max_num_seqs
        self.max_num_batched_tokens = config.max_num_batched_tokens
        self.eos = config.eos
        self.block_size = config.kvcache_block_size
        self.block_manager = BlockManager(config.num_kvcache_blocks, config.kvcache_block_size)
        self.waiting: deque[Sequence] = deque()    # 第3部分 C4: deque
        self.running: deque[Sequence] = deque()
```

#### schedule() 第一段：Prefill

```python
def schedule(self):
    scheduled_seqs = []
    num_batched_tokens = 0

    # ===== Prefill 段：优先处理 waiting =====
    while self.waiting and len(scheduled_seqs) < self.max_num_seqs:
        seq = self.waiting[0]
        remaining = self.max_num_batched_tokens - num_batched_tokens
        if remaining == 0: break
        if not seq.block_table:                                   # 新序列，还没分配块
            num_cached_blocks = self.block_manager.can_allocate(seq)
            if num_cached_blocks == -1: break                     # 显存不够，停
            num_tokens = seq.num_tokens - num_cached_blocks * self.block_size
        else:                                                      # chunked prefill 续算
            num_tokens = seq.num_tokens - seq.num_cached_tokens
        if remaining < num_tokens and scheduled_seqs: break       # ★ 只对第一个seq chunked
        if not seq.block_table:
            self.block_manager.allocate(seq, num_cached_blocks)
        seq.num_scheduled_tokens = min(num_tokens, remaining)     # ★ chunked prefill: 可能切分
        num_batched_tokens += seq.num_scheduled_tokens
        if seq.num_cached_tokens + seq.num_scheduled_tokens == seq.num_tokens:
            seq.status = SequenceStatus.RUNNING                   # 整个 prefill 完成
            self.waiting.popleft()
            self.running.append(seq)
        scheduled_seqs.append(seq)

    if scheduled_seqs:
        return scheduled_seqs, True   # is_prefill=True
```

**逐行要点**：

- `seq.waiting[0]` + `popleft()`：FIFO，先来先服务。
- `num_cached_blocks * self.block_size`：命中前缀的 token **不用算**（直接复用），从 num_tokens 里扣掉 → 这就是 prefix cache 省计算的代码体现。
- `seq.num_scheduled_tokens = min(num_tokens, remaining)`：**chunked prefill 的核心**。prompt 太长放不下，就只算 `remaining` 个，剩下的下一步。
- 只有当 `num_cached_tokens + num_scheduled_tokens == num_tokens`（整个 prompt 都算完了），序列才从 WAITING → RUNNING。中间状态仍是 prefill。

#### schedule() 第二段：Decode

```python
    # ===== Decode 段：running 序列各前进一步 =====
    while self.running and len(scheduled_seqs) < self.max_num_seqs:
        seq = self.running.popleft()
        while not self.block_manager.can_append(seq):            # 显存不够扩块
            if self.running:
                self.preempt(self.running.pop())                 # 抢占最后进的
            else:
                self.preempt(seq)                                # 没人可抢，抢自己
                break
        else:                                                     # 第3部分 D1: while...else
            seq.num_scheduled_tokens = 1                          # decode 每步 1 token
            seq.is_prefill = False
            self.block_manager.may_append(seq)                   # 需要新块就领
            scheduled_seqs.append(seq)
    assert scheduled_seqs
    self.running.extendleft(reversed(scheduled_seqs))            # 第3部分 C4: 保持顺序放回
    return scheduled_seqs, False   # is_prefill=False
```

**逐行要点**：

- `while not can_append: preempt`：显存不够时，**循环抢占**直到够（或把当前 seq 也抢了）。这是 [第 2b 部分 §5.4](02b-引擎核心机制.md) 的 preemption。
- `while...else`（[第 3 部分 D1](03-Python语法清单.md)）：抢占循环若**正常结束**（没 break，即 can_append 成了），执行 `else` 块（正常 append）。
- `extendleft(reversed(...))`：把本轮 scheduled 的序列**按原顺序**放回 running 队首。`extendleft` 本会逆序，加 `reversed` 抵消，保序。

#### postprocess：跑完后的收尾

```python
def postprocess(self, seqs, token_ids, is_prefill):
    for seq, token_id in zip(seqs, token_ids):
        self.block_manager.hash_blocks(seq)                      # ① 登记 prefix cache 哈希
        seq.num_cached_tokens += seq.num_scheduled_tokens
        seq.num_scheduled_tokens = 0
        if is_prefill and seq.num_cached_tokens < seq.num_tokens:
            continue                                              # ② chunked prefill 中途，不采样
        seq.append_token(token_id)                               # ③ 追加新 token
        if (not seq.ignore_eos and token_id == self.eos) or seq.num_completion_tokens == seq.max_tokens:
            seq.status = SequenceStatus.FINISHED                 # ④ 完成
            self.block_manager.deallocate(seq)
            self.running.remove(seq)
```

### 2.4 [`engine/llm_engine.py`](../nanovllm/engine/llm_engine.py) —— 总指挥

#### `__init__`：启动多进程 + 装配

```python
def __init__(self, model, **kwargs):
    config_fields = {field.name for field in fields(Config)}              # 第3部分 A3
    config_kwargs = {k: v for k, v in kwargs.items() if k in config_fields}
    config = Config(model, **config_kwargs)
    Sequence.block_size = config.kvcache_block_size
    self.ps = []
    self.events = []
    ctx = mp.get_context("spawn")                                          # 第3部分 E1: 必须 spawn
    for i in range(1, config.tensor_parallel_size):                        # rank 1, 2, ...
        event = ctx.Event()
        process = ctx.Process(target=ModelRunner, args=(config, i, event))
        process.start()
        self.ps.append(process); self.events.append(event)
    self.model_runner = ModelRunner(config, 0, self.events)                # rank 0 在主进程
    self.tokenizer = AutoTokenizer.from_pretrained(config.model, use_fast=True)
    config.eos = self.tokenizer.eos_token_id                               # 填 eos
    self.scheduler = Scheduler(config)
    atexit.register(self.exit)                                             # 注册退出清理
```

- 多进程启动张量并行（[第 3 部分 E1](03-Python语法清单.md)、[第 2c 部分 §2](02c-加速并行与采样.md)）。rank 0 在主进程，rank 1+ 各开一个进程。
- `atexit.register(self.exit)`：进程退出时自动清理（关共享内存、join 子进程）。

#### `step()`：一步推理

```python
def step(self):
    seqs, is_prefill = self.scheduler.schedule()          # ① 调度：决定算哪些
    num_tokens = sum(seq.num_scheduled_tokens for seq in seqs) if is_prefill else -len(seqs)
    token_ids = self.model_runner.call("run", seqs, is_prefill)   # ② 反射调用 run（第3部分 D3）
    self.scheduler.postprocess(seqs, token_ids, is_prefill)       # ③ 收尾
    outputs = [(seq.seq_id, seq.completion_token_ids) for seq in seqs if seq.is_finished]
    return outputs, num_tokens
```

> `num_tokens` 的正负号技巧：prefill 时返回**正的**总 token 数（用于算 prefill 吞吐）；decode 时返回**负的**序列数（`-len(seqs)`），调用方用 `-num_tokens` 还原成序列数算 decode 吞吐。一个变量两种含义，靠正负区分——简洁但需要适应。

#### `generate()`：用户入口的主循环

```python
def generate(self, prompts, sampling_params, use_tqdm=True):
    pbar = tqdm(total=len(prompts), ...)
    if not isinstance(sampling_params, list):
        sampling_params = [sampling_params] * len(prompts)    # 单个参数广播给所有 prompt
    for prompt, sp in zip(prompts, sampling_params):
        self.add_request(prompt, sp)                          # 全部加入 waiting
    outputs = {}
    prefill_throughput = decode_throughput = 0.
    while not self.is_finished():                             # 主循环
        t = perf_counter()
        output, num_tokens = self.step()                      # 跑一步
        if num_tokens > 0:
            prefill_throughput = num_tokens / (perf_counter() - t)
        else:
            decode_throughput = -num_tokens / (perf_counter() - t)
        pbar.set_postfix({"Prefill": f"{int(prefill_throughput)}tok/s",
                          "Decode": f"{int(decode_throughput)}tok/s"})
        for seq_id, token_ids in output:
            outputs[seq_id] = token_ids
            pbar.update(1)
    pbar.close()
    outputs = [outputs[seq_id] for seq_id in sorted(outputs.keys())]   # 按 seq_id 排序
    outputs = [{"text": self.tokenizer.decode(token_ids), "token_ids": token_ids} for token_ids in outputs]
    return outputs
```

**完整生命周期**（对应 [第 1 部分 §1.2](01-全局视角.md)）：

1. 把所有 prompt tokenize 后加入 scheduler 的 waiting 队列。
2. `while not is_finished`：反复 `step()`，每步 prefill 一批或 decode 一步。
3. 实时显示 prefill/decode 吞吐（你跑 example 时看到的进度条后缀）。
4. 收集已完成的序列，按 seq_id 排序（保证输出顺序 = 输入顺序）。
5. detokenize 还原成文字返回。

> 💡 注意：所有 prompt 是**一开始就全加入** waiting 的（不是一条条来）。然后引擎自行决定先 prefill 谁、怎么拼批——这就是 continuous batching 的"持续喂入"。

## 本篇小结

你现在能逐行读懂入口层和引擎层了：

- **入口层**：`LLM` 是 `LLMEngine` 别名；`Config` 装所有旋钮并在 post_init 校验；`SamplingParams` 禁止 temperature=0。
- **Sequence**：请求档案袋，关键是几组长度字段、block_table（页表）、`__getstate__/__setstate__`（省传输）。
- **BlockManager**：PagedAttention（block/slot/block_table）+ Prefix Caching（链式哈希 + 引用计数），代码里到处是精妙技巧（取模判断新块、哈希命中校验内容、最后一块不匹配）。
- **Scheduler**：schedule() 两段式（prefill 优先 + decode 拼批），实现 chunked prefill（min 切分）、preemption（抢占循环）、continuous batching（动态拼批）。
- **LLMEngine**：多进程启动 TP，step() 串起 schedule→run→postprocess，generate() 主循环。
