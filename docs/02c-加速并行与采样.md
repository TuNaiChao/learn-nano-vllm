## 1. Flash Attention：分块 + online softmax ⭐

对应代码：[`layers/attention.py`](../nanovllm/layers/attention.py)

### 1.1 标准 Attention 的"显存炸弹"

第 1 部分我们算过 attention 的 FLOPs，但没说它的**显存开销**。朴素实现 attention：

$$
S = QK^\top \in \mathbb{R}^{N\times N}, \quad P = \text{softmax}(S) \in \mathbb{R}^{N\times N}, \quad O = PV
$$

注意 $S$ 和 $P$ 都是 $N \times N$ 的矩阵（$N$ 是序列长度）。要**在显存里实例化**它们。当 $N = 8192$ 时，$N^2 = 67\text{M}$ 个元素，多头多层叠起来显存爆炸。更要命的是：计算时要在 **HBM（显存）和 SRAM（片上缓存）之间反复搬运**这些大矩阵。

### 1.2 先建立硬件直觉：HBM vs SRAM

```
GPU 存储层次（以 A100 为例）:

  HBM（显存）        ~80 GB    带宽 ~2.0 TB/s    （大但相对慢）
     ↕ 数据搬运（这是 attention 的真正瓶颈！）
  SRAM（片上缓存）   ~192 KB/SM  带宽 ~19 TB/s    （小但极快，约 13×）
```

**核心矛盾**：计算要的数据得先进 SRAM，但 SRAM 太小（KB 级），放不下 $N \times N$ 的大矩阵。于是朴素 attention 不得不"算一点、写回 HBM、再读回来"，反复在慢速 HBM 上读写 $N^2$ 规模的数据。

> 💡 这正是第 1 部分讲的"算术强度"问题的具象：attention 的瓶颈不是"算"，而是"搬"（IO）。Flash Attention 的目标就是**减少 HBM 读写**。

### 1.3 标准 Attention 的 IO 复杂度

朴素地算一次 attention（单头），需要读写 HBM 多少字？

- 读 $Q, K, V$：各 $N \times d$ → $O(Nd)$
- 写 $S = QK^\top$ 到 HBM、再读回来算 softmax：$O(N^2)$
- 写 $P$ 到 HBM、再读回来算 $PV$：$O(N^2)$
- 写 $O$：$O(Nd)$

合计 **HBM IO $\approx \Theta(Nd + N^2)$**，且需要 **$\Theta(N^2)$ 的额外 HBM 存储**（存 $S, P$）。

### 1.4 Flash Attention 的两大创新

**创新一：分块（Tiling）**——不实例化完整的 $N \times N$ 矩阵，而是把 $Q, K, V$ 切成小块，每块小到能放进 SRAM，在 SRAM 里算完，只把最终结果 $O$ 写回 HBM。

**创新二：online softmax**——softmax 本来需要"看到整行才能归一化"（要算整行的 max 和 sum）。Flash Attention 用一种**流式算法**，边读块边增量更新 max 和 sum，不必回头读已处理的块。

### 1.5 online softmax 推导（核心数学）

标准 softmax：对向量 $x \in \mathbb{R}^N$，

$$
m = \max_i x_i, \quad \ell = \sum_j e^{x_j - m}, \quad \text{softmax}(x_i) = \frac{e^{x_i - m}}{\ell}
$$

（减去 max $m$ 是为了数值稳定，避免 $e^{x_j}$ 溢出。）

现在把 $x$ 分成两块 $x^{(1)}, x^{(2)}$，**已经算出了第一块的 $m^{(1)}, \ell^{(1)}$**。如何在不重新读 $x^{(1)}$ 的情况下，得到整体的 $m, \ell$？

**更新 max**：

$$
m = \max(m^{(1)}, m^{(2)})
$$

**更新 sum**（关键）：第一块的 $\ell^{(1)} = \sum_{j \in \text{块1}} e^{x_j - m^{(1)}}$，是相对于 $m^{(1)}$ 算的。现在基准变成了 $m$，要 rescale：

$$
\ell = \underbrace{\ell^{(1)} \cdot e^{m^{(1)} - m}}_{\text{把块1的sum重新基准到 }m} + \underbrace{\sum_{j \in \text{块2}} e^{x_j - m}}_{\text{块2的sum}}
$$

> 🏆 **就这样！** 只需保留 $(m^{(1)}, \ell^{(1)})$ 两个标量，加上新块的数据，就能增量更新出全局 $(m, \ell)$。无需回头读旧块。这就是"online"——流式处理。

对输出 $O$ 同理：每个块算出的部分输出要按 $e^{m_{\text{old}} - m_{\text{new}}}$ rescale 后再累加。

### 1.6 Flash Attention 的 IO 复杂度

分块后，块大小 $B_r \times B_c$ 受 SRAM 大小 $M$ 约束（$B_r, B_c$ 要能和 $d$ 一起放进 SRAM）。遍历所有 $Q$ 块、$K/V$ 块的组合：

$$
\text{HBM IO} \approx \Theta\!\left(\frac{N^2 d^2}{M}\right)
$$

且**额外 HBM 存储降到 $\Theta(N)$**（不再存 $N \times N$ 的 $S, P$）。

| | 标准 Attention | Flash Attention |
|---|---|---|
| HBM IO | $\Theta(Nd + N^2)$ | $\Theta(N^2 d^2 / M)$（$M$ 是 SRAM） |
| 额外显存 | $\Theta(N^2)$ | $\Theta(N)$ |
| 实际效果 | 慢、爆显存 | 快、省显存 |

> 🔬 当 $M$（SRAM）相对 $d$ 足够大时，$\Theta(N^2 d^2 / M) < \Theta(N^2)$，即 IO 更少。结合 SRAM 比 HBM 快约 13 倍，总加速非常可观。**Flash Attention 不是减少了 FLOPs（FLOPs 其实略增），而是大幅减少了慢速 HBM 的读写**。

### 1.7 nano-vllm 用到的两个 Flash Attention 接口

[`layers/attention.py`](../nanovllm/layers/attention.py) 里，Prefill 和 Decode 用了**不同**的 flash 接口，对应两种不同的布局：

**Prefill → `flash_attn_varlen_func`（变长）**：

一个 batch 里多个序列长度不一，把它们"拼接"成一个长序列，用 `cu_seqlens`（累积长度）记录每个序列的边界。这样不用 padding 到等长，零浪费。

```
batch 里有 3 个序列，长度 3, 2, 4:
  拼接后:   [t t t | t t | t t t t]     ← 共 9 个 token，连续摆放
  cu_seqlens_q = [0, 3, 5, 9]            ← 累积边界：第0个序列[0:3), 第1个[3:5), 第2个[5:9)
  flash_attn 按 cu_seqlens 切分，每个序列内部做 causal attention，序列之间互不可见
```

**Decode → `flash_attn_with_kvcache`**：

每步每个序列只有 1 个新 query，但要和**全部历史 KV**（存在 paged cache 里）算 attention。这个接口直接吃 `block_table` 和 `cache_seqlens`，在 paged KV cache 上做 attention。

```python
o = flash_attn_with_kvcache(
    q.unsqueeze(1),              # [bs, 1, heads, dim]  每个序列1个query
    k_cache, v_cache,            # paged KV cache
    cache_seqlens=context.context_lens,   # 每个序列历史长度
    block_table=context.block_tables,     # 页表：物理块在哪
    causal=True,
)
```

> 💡 两个接口对应第 1 部分讲的两种瓶颈：varlen 服务 compute-bound 的 prefill（高效大矩阵），with_kvcache 服务 memory-bound 的 decode（直接在 cache 上算）。

### 1.8 把新 K/V 写进 cache：Triton kernel

Flash Attention 读历史 KV 没问题，但**新算出来的 K/V 怎么写进 paged cache？** 因为 slot 是散落的（不同 token 的 slot 不连续），普通 PyTorch 操作低效。nano-vllm 用一个 **Triton kernel** [`store_kvcache`](../nanovllm/layers/attention.py) 做散射写入：

```python
@triton.jit
def store_kvcache_kernel(key_ptr, ..., slot_mapping_ptr, D: tl.constexpr):
    idx = tl.program_id(0)              # 第 idx 个 token
    slot = tl.load(slot_mapping_ptr + idx)   # 它的全局 slot
    if slot == -1: return               # -1 = 跳过（CUDA graph 填充的占位）
    # 从 key 指针读出这个 token 的 K，写到 cache 的 slot 位置
    key = tl.load(key_ptr + idx*stride + arange(0, D))
    tl.store(k_cache_ptr + slot*D + arange(0, D), key)
```

- **Triton 是什么**：OpenAI 出的"用 Python 写 GPU kernel"的语言/编译器。你写 Python 风格代码，它编译成接近手写 CUDA 性能的 kernel。比学 CUDA C 门槛低很多。
- `tl.program_id(0)`：当前线程块（处理第 idx 个 token），`tl.arange(0, D)` 生成 `[0,1,...,D-1]` 索引，`tl.load/tl.store` 显式读写显存。
- 这里 `slot == -1` 的判断很重要：CUDA graph 回放时 batch 是固定大小的，实际序列数可能少于 batch，多出来的位置 slot 填 -1，kernel 跳过它们。

## 2. Tensor Parallelism：把大矩阵切给多张卡 ⭐

对应代码：[`layers/linear.py`](../nanovllm/layers/linear.py)、[`layers/embed_head.py`](../nanovllm/layers/embed_head.py)

### 2.1 为什么要张量并行

单个大模型可能放不下一张卡，或者单卡算太慢。**张量并行（Tensor Parallelism, TP）** 的思路：不切模型"层"（那是流水线并行），而是**切每一层内部的矩阵**，让多张卡同时算同一个矩阵乘法，再通信合并。

```
单卡:    Y = X @ A        (一个大矩阵乘，慢)

TP 切矩阵 A，多卡并行:
  卡0: Y_0 = X @ A_0  ─┐
  卡1: Y_1 = X @ A_1  ─┤── 通信合并 ──▶ Y
  卡2: Y_2 = X @ A_2  ─┤
  卡3: Y_3 = X @ A_3  ─┘
```

### 2.2 两种基本切法：列并行 vs 行并行

矩阵乘 $Y = XA$，其中 $X \in \mathbb{R}^{b \times k}$，$A \in \mathbb{R}^{k \times n}$，$Y \in \mathbb{R}^{b \times n}$。

**列并行（Column Parallel）**——把 $A$ 按**列**（输出维度 $n$）切：

```
A = [A_0 | A_1 | ... | A_{p-1}]    每块 A_i ∈ ℝ^{k × n/p}

每卡 i:  Y_i = X @ A_i  ∈ ℝ^{b × n/p}     ← 每卡拿到 Y 的不同"列"
```

- 每卡有**完整的 X**，只算**自己那份输出列**。
- 结果 $Y = [Y_0 | Y_1 | ... | Y_{p-1}]$，拼起来才是完整 Y（但通常不拼，直接进入下一个列并行的 op）。

**行并行（Row Parallel）**——把 $A$ 按**行**（输入维度 $k$）切，同时把 $X$ 按列切：

```
A = [A_0; A_1; ...; A_{p-1}]    每块 A_i ∈ ℝ^{k/p × n}     (竖着切)
X = [X_0 | X_1 | ... | X_{p-1}]  每块 X_i ∈ ℝ^{b × k/p}    (横着切)

每卡 i:  Y_i = X_i @ A_i  ∈ ℝ^{b × n}     ← 每卡算出 Y 的"部分和"

完整 Y = Σ_i Y_i  (需要 all_reduce 求和)
```

- 每卡只有**自己那份 X**，算出 $Y$ 的部分和。
- 结果要 **all_reduce**（跨卡求和）才得到完整 Y。

### 2.3 经典组合：一个 MLP 只通信一次 ⭐

Megatron-LM 发现了一个绝妙组合。MLP 是两层线性变换夹激活：

$$
Y = \text{act}(X W_1) \cdot W_2
$$

让 $W_1$ 用**列并行**，$W_2$ 用**行并行**：

```
X (每卡完整)
  │
  ▼ W_1 列并行 (切成 W_1^0...W_1^{p-1})
卡i: H_i = act(X @ W_1^i)     ← 列并行结果：每卡拿到不同列，无需通信！
  │                              （act 是逐元素的，列并行天然兼容）
  ▼ W_2 行并行 (切成 W_2^0...W_2^{p-1})
卡i: Y_i = H_i @ W_2^i        ← 行并行：每卡算部分和
  │
  ▼ all_reduce
Y = Σ_i Y_i                   ← 只在这里通信 1 次！
```

> 🏆 **关键洞察**：列并行的输出"列"，正好是行并行需要的输入"列分"。中间的激活层不需要任何通信。**整个两层 MLP 只需在最末尾做 1 次 all_reduce**。这是 TP 高效的精髓。

Attention 层同理：QKV 投影列并行，输出投影（$O$）行并行，中间不需要通信，末尾 1 次 all_reduce。

### 2.4 通信量推导 ⭐

一次 all_reduce 要传输多少数据？

- all_reduce 的语义：每卡有一个同样大小的张量，最后每卡都得到它们的和。
- 用 **Ring-AllReduce** 算法（最常用）：把数据分 $p$ 段，环形传递，**每个节点**的通信量 $\approx \frac{2(p-1)}{p} \cdot \text{data\_size}$（$p$ 是卡数；$p$ 大时趋近 $2\times$ 数据量，$p{=}2$ 时约为 $1\times$）。
- 简化估算：**约 $2 \times$ 张量大小**（send 一次 + recv 一次）。

all_reduce 的张量是 $Y \in \mathbb{R}^{b \times n}$（$b$ = batch×seq，$n$ = hidden_size）。所以：

$$
\text{每层 all\_reduce 通信量} \approx 2 \cdot b \cdot n \cdot \text{dtype\_bytes}
$$

每个 Transformer 层有 **2 次** all_reduce（attention 的 o_proj 后、MLP 的 down_proj 后各一次）：

$$
\text{每步每层通信} \approx 4 \cdot b \cdot n \cdot \text{bytes}
$$

**通信 vs 计算的权衡**：

| | 通信量 | 计算量 |
|---|---|---|
| 单层（TP） | $\Theta(b \cdot n)$（与卡数无关） | 每卡 $\Theta(b \cdot n^2 / p)$ |
| 算术强度 | — | 随 $p$ 增大，每卡算的少，但通信不变 |

> 📉 **结论**：TP 在 $b$（batch×seq）大时划算（通信被大量计算摊薄）；$b$ 小时（比如 decode 每步 batch 可能不大），通信占比上升，TP 效率下降。这也是为什么 TP 通常结合较大的 batch 用。nano-vllm 的 decode 把多个序列拼成一个大 batch，部分原因就是让 TP 更划算。

### 2.5 QKV 打包：三个矩阵合一

Attention 的 $W_Q, W_K, W_V$ 三个矩阵都接收同一个 $X$。和 SwiGLU 同理，把它们**合并成一个胖矩阵**一次算（[`QKVParallelLinear`](../nanovllm/layers/linear.py)）：

```
合并后 W = [W_Q | W_K | W_V]   一次矩阵乘 → [Q | K | V]，再 split 成三份
```

而且这三个矩阵各自的列并行切法不同（Q 头多，KV 头少，因 GQA），[`QKVParallelLinear.weight_loader`](../nanovllm/layers/linear.py) 要按 q/k/v 分别定位切分。这就是为什么 [`Qwen3ForCausalLM.packed_modules_mapping`](../nanovllm/models/qwen3.py) 要记录 `q_proj→qkv_proj` 这种映射——加载 HuggingFace 权重时，把分开的 q/k/v 装进合并的胖矩阵。

### 2.6 weight_loader：按 rank 切分加载

每张卡只持有权重的一部分。加载时要按 `rank` 把完整权重的对应切片拷给本卡（[`ColumnParallelLinear.weight_loader`](../nanovllm/layers/linear.py)）：

```python
def weight_loader(self, param, loaded_weight):
    shard_size = param.data.size(self.tp_dim)
    start_idx = self.tp_rank * shard_size        # 本卡负责的起始位置
    loaded_weight = loaded_weight.narrow(self.tp_dim, start_idx, shard_size)  # 切片
    param.data.copy_(loaded_weight)              # 拷给本卡
```

> `narrow(dim, start, length)` 是 PyTorch 的"切片"操作，**零拷贝视图**——它不复制数据，只是返回原张量某一片段的 view。第 3/4 部分会细讲。

### 2.7 VocabParallelEmbedding / ParallelLMHead

Embedding 和 LM Head 涉及 vocab 维度（词表很大），也按词表切（[`embed_head.py`](../nanovllm/layers/embed_head.py)）：

- **Embedding（列并行）**：每卡只持有词表的一段 token embedding。查表时，不在自己段的 token 输出 0，最后 all_reduce 求和。
- **LM Head（行并行 + gather）**：每卡算自己那段词表的 logits，rank 0 用 `gather` 收集所有卡的 logits 拼成完整词表分布（[`ParallelLMHead`](../nanovllm/layers/embed_head.py)）。

## 3. CUDA Graph：专治 Decode 的调度开销 ⭐

对应代码：[`engine/model_runner.py`](../nanovllm/engine/model_runner.py) 的 `capture_cudagraph` / `run_model`

### 3.1 问题：Decode 时 CPU 调度成了瓶颈

回顾第 1 部分：decode 是 **memory-bound**，每步 GPU 实际计算时间 $T_{\text{compute}}$ 很短。但每步推理要发射**很多个 GPU kernel**（28 层 × 每层若干算子 = 上百个 kernel）。每发射一个 kernel，CPU 都有调度开销：

$$
T_{\text{step}} = \underbrace{T_{\text{launch}}}_{\text{CPU 调度开销}} + \underbrace{T_{\text{compute}}}_{\text{GPU 计算时间}}
$$

- $T_{\text{launch}} \approx N_{\text{kernels}} \times \delta$，每个 kernel launch 开销 $\delta \approx$ 几微秒。
- decode 时上百个 kernel，$T_{\text{launch}}$ 可达 $0.5\text{ms}+$。
- 而 decode 的 $T_{\text{compute}}$ 可能也只有亚毫秒级。

结果：**$T_{\text{launch}}$ 和 $T_{\text{compute}}$ 一个量级，CPU 调度开销占比惊人**！CPU 成了"喂不饱 GPU"的瓶颈。

```
Decode 一步（无 CUDA Graph）:
  CPU: [launch][launch][launch]......[launch]   ← 上百次调度，CPU 忙死
  GPU:        idle   算    idle   算   ...       ← GPU 等待，算力闲置

  T_step ≈ T_launch + T_compute，T_launch 占比大
```

### 3.2 CUDA Graph 的开销模型

CUDA Graph 把"一整步的所有 kernel"**录制**成一张图，以后每次**回放（replay）**这张图，只需一次提交，省掉所有逐个 launch 的开销：

$$
T_{\text{step}}^{\text{graph}} = \underbrace{T_{\text{replay}}}_{\text{很小}} + T_{\text{compute}} \;\approx\; T_{\text{compute}}
$$

$T_{\text{replay}}$ 远小于 $T_{\text{launch}}$（一次提交整张图 vs 上百次单独 launch）。

```
Decode 一步（有 CUDA Graph）:
  先录制一次:  CPU 把所有 kernel 依赖关系录成"图"
  之后每步:    CPU: [replay]                    ← 一次提交！
              GPU: 算算算算算算算算算算算算算算    ← 连续计算，无空隙

  T_step ≈ T_compute，开销被消除 ✅
```

> 🎯 **这就是为什么 CUDA Graph 对 decode 提速巨大**：它精准消除了 decode 里占比很大的 $T_{\text{launch}}$。而 prefill 是 compute-bound，$T_{\text{compute}}$ 远大于 $T_{\text{launch}}$，graph 收益小——所以 nano-vllm **只在 decode 用 graph，prefill 不用**。

### 3.3 为什么 capture 要"按 batch size 离散桶"

CUDA Graph 录制时的**张量形状是固定的**（形状写死在图里）。但 decode 时 batch size 会变（Continuous Batching 动态增减序列）。怎么办？

nano-vllm 的做法：**预先录制若干个"桶"大小的图**（[`capture_cudagraph`](../nanovllm/engine/model_runner.py)）：

```python
self.graph_bs = [1, 2, 4, 8] + list(range(16, max_bs + 1, 16))   # 1,2,4,8,16,32,48,...
for bs in reversed(self.graph_bs):
    graph = torch.cuda.CUDAGraph()
    # warmup（必须，让内存分配稳定）
    outputs[:bs] = self.model(input_ids[:bs], positions[:bs])
    # 正式录制
    with torch.cuda.graph(graph, self.graph_pool):
        outputs[:bs] = self.model(input_ids[:bs], positions[:bs])
    self.graphs[bs] = graph
```

回放时，按实际 batch 大小 $b$，**向上取最近的桶**：

```python
graph = self.graphs[next(x for x in self.graph_bs if x >= bs)]   # 找 ≥b 的最小桶
graph_vars["input_ids"][:bs] = input_ids   # 把实际数据填进桶的前 bs 个位置
graph_vars["slot_mapping"].fill_(-1)        # 多余位置填 -1（让 kernel 跳过）
graph.replay()                              # 回放
return self.model.compute_logits(graph_vars["outputs"][:bs])   # 只取前 bs 个结果
```

- 多出来的位置（`bs` 到桶大小）填**占位值**（slot_mapping 填 -1），让 kernel 跳过它们——这正是 §1.8 那个 `if slot == -1: return` 的用途！
- 用 `reversed` 录制 + 共享 `graph_pool`：让所有图共用一块显存池，省显存（细节第 4 部分讲）。

> ⚠️ 录制前必须 **warmup**（先跑一次）：CUDA 内存的分配/缓存策略在第一次跑时会变化，必须等它稳定后录制，否则图里的内存地址会错乱。

### 3.4 何时不用 graph

```python
if is_prefill or self.enforce_eager or input_ids.size(0) > 512:
    return self.model.compute_logits(self.model(input_ids, positions))  # 正常跑
else:
    ...graph.replay()...
```

- prefill：不用（compute-bound，且形状多变）。
- `enforce_eager`：用户选择强制 eager（调试用）。
- batch > 512：超过最大桶，退回 eager。

## 4. torch.compile：算子融合

散落在 [`RMSNorm`](../nanovllm/layers/layernorm.py)、[`RotaryEmbedding`](../nanovllm/layers/rotary_embedding.py)、[`SiluAndMul`](../nanovllm/layers/activation.py)、[`Sampler`](../nanovllm/layers/sampler.py) 上的 `@torch.compile`。

### 4.1 原理

`torch.compile`（PyTorch 2.0+）会把一个函数里**多个细碎的 PyTorch 算子**编译、**融合（fuse）成少数几个 GPU kernel**。

以 RMSNorm 为例，原始代码有：`pow`、`mean`、`add`(eps)、`rsqrt`、`mul`、`mul`(weight)——6 个算子。不融合的话，每个算子都是一次 kernel launch + 一次显存读写中间结果：

```
不融合（6 次 launch + 5 次中间显存读写）:
  x → [pow]→tmp1 → [mean]→tmp2 → ... → 输出
        HBM↕        HBM↕
```

`@torch.compile` 融合后，变成 1~2 个 kernel，中间结果留在 SRAM/寄存器里：

```
融合后（1~2 次 launch，中间结果不落 HBM）:
  x → [融合kernel: 平方+均值+开方+缩放+乘权重] → 输出
```

### 4.2 收益

- **减少 kernel launch 开销**（6 次 → 1~2 次）。对 decode 这种 launch 开销敏感的场景尤其重要（和 CUDA Graph 互补）。
- **减少 HBM 读写**（中间结果不落盘）。访存密集的场景收益大。

> 🔬 `torch.compile` 底层是 Dynamo（追踪 Python 字节码）+ Inductor（生成 Triton 代码）。融合后生成的也是 Triton kernel——和 §1.8 手写的 store_kvcache 同属一种技术。

## 5. 采样：一行代码背后的 Gumbel-max 数学 ⭐

对应代码：[`layers/sampler.py`](../nanovllm/layers/sampler.py)

### 5.1 从 logits 到 token

模型最后输出 **logits**（每个词的原始分数）。采样要把它变成"下一个 token"。流程：

```
logits [vocab]  ──÷T──▶  logits/T  ──softmax──▶  probs [vocab]  ──采样──▶  1 个 token id
```

- $T$ 是 **temperature**：$T$ 大 → 分布更平坦（更有创造力/随机）；$T$ 小 → 更尖锐（更确定）；$T \to 0$ 退化成贪心（argmax）。nano-vllm 甚至**禁止 $T=0$**（[`sampling_params.py`](../nanovllm/sampling_params.py) 里 `assert temperature > 1e-10`）。

### 5.2 朴素采样的痛点

从概率分布 `probs` 采样一个 token，最直接的是 `torch.multinomial(probs)`。但 `multinomial` 内部要构建 CDF（累积分布）并二分查找，批量、不同 temperature 时不那么高效。nano-vllm 用了一个更巧的等价方法。

### 5.3 nano-vllm 的实现

```python
class Sampler(nn.Module):
    @torch.compile
    def forward(self, logits, temperatures):
        logits = logits.float().div_(temperatures.unsqueeze(dim=1))   # logits / T
        probs = torch.softmax(logits, dim=-1)                          # 概率分布
        sample_tokens = probs.div_(                                    # ★ Gumbel-max 变体
            torch.empty_like(probs).exponential_(1).clamp_min_(1e-10)
        ).argmax(dim=-1)
        return sample_tokens
```

核心是那句 `probs / exponential(1)` 取 argmax。这为什么能正确采样？我们来推导。

### 5.4 Gumbel-max 原理（硬核推导）

**目标**：从 $\text{Categorical}(p_1, ..., p_V)$ 采样一个下标（$\sum_i p_i = 1$）。

**经典 Gumbel-max 定理**：若 $G_i \overset{\text{iid}}{\sim} \text{Gumbel}(0)$，则

$$
\arg\max_i \big(\log p_i + G_i\big) \;\sim\; \text{Categorical}(p)
$$

（Gumbel 分布的 CDF 是 $F(x) = e^{-e^{-x}}$，可由 $G = -\log(-\log U),\; U \sim \text{Uniform}(0,1)$ 生成。）

### 5.5 nano-vllm 用的等价形式：Exp 变体

> 📝 **记号约定**：本文 $\text{Exp}(\lambda)$ 指 **rate 参数化**（密度函数 $\lambda e^{-\lambda x}$，均值 $1/\lambda$），不是 scale 参数化。下面的缩放性质都基于此。

nano-vllm 没用 $\log p_i + G_i$，而是用 `probs / exponential(1)`，即 $\arg\max_i (p_i / E_i)$，其中 $E_i \overset{\text{iid}}{\sim} \text{Exp}(1)$（指数分布，rate=1）。我们来证明它等价：

**证明**：$\arg\max_i (p_i / E_i)$ 等价于 $\arg\min_i (E_i / p_i)$。

令 $T_i = E_i / p_i$。因为 $E_i \sim \text{Exp}(1)$，对 $c > 0$ 有 $c \cdot E_i \sim \text{Exp}(1/c)$（指数分布的缩放性质）。所以

$$
T_i = \frac{E_i}{p_i} \sim \text{Exp}(p_i)
$$

现在比较若干独立的指数分布 $T_i \sim \text{Exp}(p_i)$ 取最小值。利用指数分布的"竞争"性质（race property）：

$$
P\!\left(\arg\min_i T_i = j\right) = \frac{p_j}{\sum_i p_i} = p_j \quad (\text{因为 } \sum_i p_i = 1)
$$

> 📐 **race property 直觉**：把每个 $\text{Exp}(p_i)$ 想象成一个"以速率 $p_i$ 响铃的闹钟"，谁先响的概率正比于它的速率 $p_i$。这正是连续时间马尔可夫链里"竞争指数分布"的经典结论。

所以 $\arg\min_i T_i \sim \text{Categorical}(p)$，即 $\arg\max_i (p_i / E_i) \sim \text{Categorical}(p)$。✅

### 5.6 为什么这个实现聪明

| 方面 | multinomial | nano-vllm 的 Gumbel-max 变体 |
|---|---|---|
| 核心运算 | 构建 CDF + 搜索 | 一次逐元素除 + argmax |
| 批量、异构 temperature | 麻烦 | 天然支持（probs 已含各自 T） |
| GPU 友好 | 一般 | 极好（全并行逐元素运算） |
| `clamp_min_(1e-10)` | — | 防 $E_i$ 过小导致除零/溢出 |

> 🎯 一行 `probs.div_(exponential_(1)).argmax()`，背后是"指数分布竞争"的优美数学，却用最 GPU 友好的方式（逐元素运算）实现了按概率采样。这是工程与数学结合的典范。

## 6. 显存预算：反推 KV cache 能开多少块

对应代码：[`allocate_kv_cache`](../nanovllm/engine/model_runner.py)

最后看一个工程问题：**KV cache 那么大张量，到底该分配多少块？**

### 6.1 思路：占满剩余显存

显存就那么多，要分给三部分：

```
总显存 total
  ├── 模型权重（固定）           ┐
  ├── 激活、临时缓冲（峰值 peak）  ├─ 这些先扣掉
  ├── CUDA context 等开销（used） ┘
  └── 剩下的全给 KV cache！
```

`gpu_memory_utilization`（默认 0.9）是一个安全系数，留 10% 余量防 OOM。

### 6.2 为什么要 warmup

激活显存是动态的（不同 batch 占的临时显存不同）。直接测当前显存不准——必须**先跑一次最大可能的 batch**（[`warmup_model`](../nanovllm/engine/model_runner.py)），把峰值激活显存"逼出来"，测准 `peak`，再算剩余。

### 6.3 公式

```python
free, total = torch.cuda.mem_get_info()
used = total - free
peak = torch.cuda.memory_stats()["allocated_bytes.all.peak"]
current = torch.cuda.memory_stats()["allocated_bytes.all.current"]

# 第 2b 部分算过的 block_bytes
block_bytes = 2 * num_hidden_layers * block_size * num_kv_heads * head_dim * dtype.itemsize

num_kvcache_blocks = int(total * util - used - peak + current) // block_bytes
```

> 为什么 `- peak + current`？`peak` 是历史峰值（包含已释放的临时显存），`current` 是当前实际占用。`peak - current` ≈ "曾经占用但现已释放的临时显存"，这部分**当前是空闲的**，所以从峰值里减掉，加回可用量。最终 `total*util - used - (peak - current)` = 扣除一切后真正可用的字节数。

这个公式就是第 1 部分 §4.3 那个"KV cache 总显存"公式的**逆运算**——先知道有多少显存，再除以每块大小，得到块数。

## 本篇小结 + 第 2 部分收官

你现在已经掌握了 nano-vllm 全部加速与采样技术的原理：

1. **Flash Attention**：分块 + online softmax（增量更新 $m, \ell$），把 HBM IO 从 $\Theta(N^2)$ 降到 $\Theta(N^2d^2/M)$，额外显存从 $\Theta(N^2)$ 降到 $\Theta(N)$。prefill 用 `varlen`（变长拼批），decode 用 `with_kvcache`（paged cache 上算）。
2. **Tensor Parallelism**：列并行（切输出维）/ 行并行（切输入维 + all_reduce）；Megatron 组合让一个 MLP 只通信 1 次；每层 2 次 all_reduce，通信量 $\Theta(b \cdot n)$。
3. **CUDA Graph**：录制 kernel 序列一次回放，消除 decode 里占比大的 $T_{\text{launch}}$；按 batch size 离散桶录制，多余位置填占位。
4. **torch.compile**：算子融合，减少 launch 和 HBM 读写。
5. **Triton kernel**：Python 写 GPU kernel，散射写 KV cache。
6. **采样**：Gumbel-max 的 Exp 变体 $\arg\max(p_i/E_i)$，用指数分布竞争性质优雅实现按概率采样。
7. **显存预算**：warmup 测 peak，`num_blocks = (total·util - used - peak + current) // block_bytes`。
